# Design — The Leighton Loop Observation Mechanism

This document proposes the design for the "Observe outcomes" arrow of the Leighton Loop, as identified as a critical dependency in `docs/leighton-weight-engine.md`.

---

## 1. The Attestation Artefact

To close the Leighton Loop, we need a mechanism to record a judgment about a past event. This mechanism is the **Attestation**.

An Attestation is a new, lightweight, signed artefact recorded on a ledger. It is not a new capsule type, but rather a specific `event.attestation.issued` event structure. It makes a specific claim about the outcome of a subject event.

An Attestation contains:
- **`subject_event_hash`**: The SHA-256 hash of the ledger entry for the event being attested to. This creates an explicit, cryptographic link.
- **`attester_id`**: The identity of the entity making the attestation (e.g., a HAL validator's DID).
- **`outcome`**: A simple, domain-defined string (e.g., "succeeded", "failed", "held", "broke", "confirmed", "refuted").
- **`rationale`**: An optional, human-readable justification for the outcome.

This Attestation becomes a new observation in the stream used to compute the original actor's λ score.

## 2. Answering the Open Questions

The `leighton-weight-engine.md` design document raised three critical questions. This design answers them as follows.

### 2.1. What generates outcome observations?

Attestations can be generated by multiple sources, with the value of their observation being a function of their own λ score.

- **HAL Validators (Primary Source):** A human validator (e.g., a `Fact Validator` or `Consequence Authoriser`) is the primary source of high-value attestations. A validator observing the result of a prior action issues a signed attestation, feeding the outcome back into the system.
- **Automated Agents:** Designated automated systems (e.g., a CI/CD pipeline, a monitoring service) can be granted the authority to issue attestations. A pipeline could attest that a build `succeeded` or `failed`, providing rapid, automated feedback.
- **Self-Attestation:** An entity can attest to the outcome of its own actions. While this has a very low initial value, it allows an entity to report its status. The trustworthiness of this self-attestation is then judged by subsequent, higher-authority attestations.

### 2.2. How long after the fact may they arrive?

This design proposes an **Attestation Window**.

- **Definition:** An Attestation Window is a configurable time period following an event, during which attestations are considered "timely."
- **Decaying Value:** An attestation's contribution to the λ calculation is highest when issued within this window. Attestations can still be issued after the window closes, but their impact (the N₀ value in the decay formula) is reduced according to a pre-defined curve. This incentivizes prompt feedback.
- **Domain-Specific Configuration:** The length of the window is not universal. It must be defined as a policy in a domain's governance capsule. A software build might have a window of 24 hours; a strategic business decision might have a window of 6 months.

### 2.3. Whether an outcome can itself be disputed, and what happens if so?

Yes, an outcome can be disputed. The system handles this elegantly without complex dispute-resolution logic.

- **Disputes are Counter-Attestations:** A dispute is simply another attestation on the same `subject_event_hash` with a conflicting `outcome`. For example, one validator attests "succeeded" while another attests "failed".
- **The Engine Resolves the Conflict:** There is no special "dispute" state. The Leighton Weight Engine resolves the conflict implicitly. It processes both attestations as standard observations. The impact of each attestation on the original actor's λ score is weighted by the λ score of the *attester*. If a high-trust validator refutes a low-trust agent's claim, the negative impact will far outweigh the positive one.
- **No Infinite Recursion:** An attestation is a primary observation about an event. While one could theoretically attest to an attestation, this design proposes that for v1, attestations only target primary ledger events. The trust system resolves disputes via the relative weight of the attesters, not by a recursive chain of judgments.

## 3. Example Flow

1.  **Action:** Agent `B-17` performs an action, recorded as ledger entry `E-123`.
2.  **Attestation 1:** HAL Validator `V-01` (high λ) observes the action succeeded and issues an `event.attestation.issued` for `E-123` with `outcome: "succeeded"`. This is recorded as ledger entry `E-128`.
3.  **Attestation 2:** Agent `M-04` (low λ) issues a counter-attestation for `E-123` with `outcome: "failed"`. This is recorded as ledger entry `E-129`.
4.  **λ Computation:** When computing Agent `B-17`'s λ score, the engine sees two new observations related to `E-123`. It applies a positive contribution from `E-128`, weighted by `V-01`'s high λ, and a negative contribution from `E-129`, weighted by `M-04`'s low λ. The net effect is a significant positive adjustment to `B-17`'s score.
